The plan in plain technical language

From public trip records
to answers we can trust.

We are building a data platform that downloads mobility data, turns it into reliable tables, keeps those tables up to date, and uses them for analysis. Then we add streaming experiments, forecasts and a public portal.

Current state: this repository has design documentation and a small Python package for validating local configuration. The data pipelines and application are still planned. Follow the reading path below to understand the goal, the design, and what implementation must prove.

01 / THE RESULT

What should this project actually do?

Start with NYC Yellow Taxi trips and taxi-zone reference data. Answer questions such as “How many pickups happened in this zone each hour?” and “How did demand change between two periods?” Every answer should identify the data period and source version behind it.

First useful result

A reproducible data pipeline

From a small source file, produce a checked demand table and a query result. Run it again without counting the same input twice. Ingest a new or corrected release without breaking an older experiment.

First public result

A small, understandable portal

Show the architecture, data coverage and measured engineering results. Publish compact data exports so the site can work while the development stack is stopped.

Later

Streaming and more sources

Replay historical records as events to test late arrivals, duplicates and recovery. Add weather, events, traffic, other taxi services and eventually Chicago.

Later

Forecasts and an analytics assistant

Evaluate demand forecasts against simple baselines. Let an assistant call controlled query tools and explain their results, with the same data and permission boundaries as the API.

Success means reproducible results and measured behavior. We do not need an enormous dataset or every tool running together to demonstrate that.

02 / HOW DATA MOVES

Follow one trip through the system

Imagine a trip picked up in zone 161 at 18:31. It eventually contributes one pickup to that zone’s hourly count.

  1. Find and download the source release

    A source adapter discovers the requested historical period or a newly published release. It records where the file came from, its checksum and its size in a manifest—an inventory of that input.

  2. Keep the original, then create Bronze tables

    Object storage keeps the original source bytes. Bronze preserves the source’s fields and provenance. Parquet is the file format; Iceberg manages which files belong to each table and version.

  3. Validate and normalize into Silver

    Check timestamps, locations, units and identity. Invalid records go to quarantine with reasons. Spark becomes the main batch engine for this step; a smaller initial writer may be used in the first milestone.

  4. Calculate Gold tables

    Aggregate the accepted trips into defined products, such as zone_hour_demand. One selected writer does this first; proposed dbt models running through Trino take over Gold in Stage 2 after compatibility tests.

  5. Publish a checked version

    Verify totals and record the exact table snapshots. A snapshot identifies a table version. Advance the public release only when the result is complete, without allowing an older job to overwrite a newer release.

  6. Show the answer

    The first portal reads versioned JSON exports of Gold. Later, FastAPI can answer runtime queries through Trino, serve model predictions or read current replay state from Redis.

Storage is not processing. MinIO stores objects. Parquet organizes columns inside files. Iceberg defines versioned tables over those files. A catalog locates and coordinates table metadata. Spark and Trino do the computation.

03 / HISTORY AND LATEST

Three workloads, with clear meanings

All three use explicit source identity and data coverage.
Workload What it means Example
Historical backfill Load selected past periods and keep a fixed version for analysis. Compare two months using the same cleaning rules.
Latest-source refresh Discover and validate new published files or corrections to older files. Add a newly released month; rebuild an affected period when its source changes.
Streaming replay Send historical records through Kafka and Flink at a controlled rate. Inject a duplicate, delay an event, restart a worker and check the final counts.

“Latest published” is not “happening now.” The source can publish records after the trips occurred. The UI must show event coverage and refresh time separately. Replay must always be labelled as simulated arrival of historical records.

Keep selected older periods and a recent window locally. A larger deployment can retain more history using the same contracts. When a source is corrected, update the affected period deliberately; do not simply append it and double the count. A failed refresh leaves the previous valid release available.

Historical experiments pin their inputs. Forecasting also needs a rule for when each feature was available: a trip’s final fare or dropoff cannot be used to predict demand at its pickup time. Initial forecasts are backtests or replay simulations, not a claim of live forecasting.

04 / WHY THESE TOOLS

Each tool has a specific job

Component Job in UrbanFlow When
Python adapters Discover releases, download files, record manifests and apply source-specific mappings. Foundation
MinIO + Parquet + Iceberg + catalog Store data and maintain shared, versioned analytical tables. The catalog product is still to be selected. Foundation
Trino / DuckDB Trino queries the lakehouse. DuckDB offers lightweight local inspection and a comparison baseline with a tested access mode. Foundation / experiments
Spark / dbt Spark owns batch cleaning into Silver. Proposed dbt-trino models own Gold; they are not competing writers for the same table. Stage 2; exact support tested first
Airflow Schedule finite refresh, backfill, modelling and maintenance jobs. With orchestration
Kafka + registry + Flink Transport versioned events and calculate event-time results with recovery state. Flink writes separate streaming tables. Streaming stage
Next.js / FastAPI / Redis Next.js is the portal. Add FastAPI for runtime features; Redis caches current state when needed. Portal first; services progressively
MLflow + models / agent tools Track forecast experiments and serve versioned predictions; provide controlled natural-language analytics. After reliable data products
Tests and telemetry Check correctness, freshness, failures and resource use. Prometheus/Grafana and other backends expand as services arrive. Basic checks from the first feature

ClickHouse, OpenMetadata, NiFi, Kubernetes, Census enrichment and extra cloud platforms are not foundation dependencies. We add them only when a defined workload justifies their cost and maintenance.

05 / BUILD ORDER

What we will implement first

  1. Prove the foundation works. Choose compatible catalog, writer and query-engine versions. Write and read a tiny Iceberg fixture. Decide source identity and correction rules.
  2. Build reliable ingestion. Discover releases, download with manifests, retry safely and enforce local resource budgets.
  3. Complete one analytical slice. Produce Bronze, Silver and Gold; quarantine bad rows; reconcile the final count. Demonstrate historical and latest refresh together.
  4. Add modelling and scheduling. Introduce Spark/dbt ownership, Airflow refresh/backfill jobs and safe table maintenance. Prove overlapping jobs do not corrupt publication.
  5. Publish evidence and a small portal. Run a controlled benchmark, export validated results and build architecture, engineering and data pages.

Then continue through streaming, additional sources/cities, ML, the agent, broader production hardening and the integrated public platform. These are the existing eight roadmap stages; the list above breaks the early work into smaller commits.

First milestone demo: start from a small fixture, run the pipeline, show a known zone/hour count, rerun without duplication, then refresh a release while the pinned historical result remains reproducible.

06 / LOCAL AND LARGER

Start small without designing a dead end

Our local operating budget

  • 16 GB RAM / 512 GB SSD host.
  • About 10 GB routine working data; at most 20 GB at peak.
  • Count raw/curated copies, snapshots, Kafka logs, checkpoints, exports and temporary rewrites.
  • Provisional 8–10 GB stack RAM; verify with measurements.
  • Run only the services needed for the current task.

The expandable architecture

  • Keep source adapters separate from transformations.
  • Configure endpoints, periods, retention and concurrency.
  • Keep table, event and API contracts versioned.
  • Allow larger storage and more workers in another deployment.
  • Test connector compatibility and recovery when moving environments.

The 20 GB limit belongs to the local profile. It is not a limit embedded in the source model, API or overall architecture. If a new download cannot fit while retaining required history, admission pauses or the workload moves; the system must not silently delete protected snapshots.

07 / PROPOSED FOLDERS

One repository, organized by responsibility

Recommendation: keep one repository and one shared Python package initially. Separate SQL models, deployable apps, orchestration and infrastructure where they have different runtimes or ownership. Create directories when their first feature arrives; this is not a request to scaffold empty folders now.

Today the repository contains documentation, HTML/diagram assets, project-specific agent skills and instructions, plus a shared Python package with a local configuration CLI, unit tests, formatting, linting, pre-commit and CI configuration. See contributor setup for runnable checks. The package, configuration and unit-test foundations exist; data jobs, services and the remaining directories in the tree below are proposed.

Why these boundaries?

FoundationSources, ingestion and lakehouse

sources/nyc_tlc/ knows where TLC files are and how their fields map. ingestion/ owns the reusable download/run lifecycle. lakehouse/ owns catalog/table interactions. A Chicago adapter should reuse the lifecycle without importing NYC-specific rules.

The first slice needs config, contracts, source/ingestion, lakehouse, quality and publication code. Add batch, replay and ML modules with their stages.

FoundationContracts, schemas and validation code

data-contracts/ describes meaning: keys, units, table grain, freshness, ownership and correction policy. schemas/ contains authoritative machine-readable shapes. src/urbanflow/contracts/ loads and validates them; it should not maintain a second handwritten schema definition. Package or mount the schemas explicitly for each runtime.

Stage 2Batch, SQL models and orchestration

batch/ contains Spark transformations. models/ contains the proposed dbt project for Gold SQL. orchestration/airflow/ schedules those jobs, passes parameters and handles dependencies. Transformation code remains testable without starting Airflow.

The first Gold writer is temporary. When dbt takes ownership, remove or retire that writer explicitly so both cannot publish the same model.

StreamingReplay and Flink

The replay producer is Python code in the shared package. Flink has a separate job/build boundary because its runtime and eventual language choice can differ. Both consume versioned contracts. Flink writes rt.zone_5min and rt.anomalies; Spark does not mutate those tables.

Product / MLApps and models

The portal is a separate Node/TypeScript app. FastAPI is a separate deployable entry point but can import the shared Python package. Training code lives in src/urbanflow/ml/; learned model binaries live in artifact storage, not the dbt models/ directory. Agent tools belong with the API initially and must enforce authorization and query limits.

Across stagesConfiguration, infrastructure and tests

configs/ stores non-secret workload settings: sources, selected periods, local limits and retention. infra/ describes how services run. Secrets enter at runtime through uncommitted environment files or a secrets service. tests/ checks code and cross-service behavior; dbt tests remain beside their SQL models. The portal keeps its framework-specific tests in its app.

Where does actual data go? Raw files, warehouse objects, checkpoints, local manifests, exports and large model artifacts belong in configured object-store locations or ignored runtime volumes outside the source tree. Only tiny fixtures and small reports belong in Git. Add the corresponding ignore rules when implementation introduces those paths.

08 / MODULE RULES

Keep the structure useful as we grow

  • Core code does not depend on the portal, API or Airflow. Apps and scheduled jobs call shared logic through entry points.
  • One owner per published table. A folder name is not enough: record writer ownership and transfer it deliberately when replacing an implementation.
  • No hard-coded laptop assumptions. Pass source periods, endpoints, budgets and retention through configuration; validate them at startup.
  • Retries must be safe. Preserve run identity, source version and expected publication predecessor so a restart does not double count or replace newer results.
  • Do not turn every folder into a service. Split a runtime only when deployment, language or scaling needs it. Keep a small number of clear entry points.
  • Changes travel with evidence. Each meaningful commit updates relevant contracts/docs and includes checks suitable for the feature.

This organization can support local profiles and larger deployments. The exact package tooling, Flink language, catalog and dbt adapter versions remain implementation decisions.
