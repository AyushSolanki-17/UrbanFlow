**Status:** Stage 1 is complete based on the evidence below; Stages 2–8 remain planned. Completion requires working artifacts and evidence, not documentation alone.

The implemented foundation includes the shared Python package, local configuration validation CLI, locked development environment, period-based Yellow Taxi acquisition with PostgreSQL provenance, a shared-catalog Iceberg/Trino compatibility path, and a reconciled first analytical slice. Stage 1 completion is recorded below. The next milestone is Stage 2 compatibility and measurement.

Initial setup verification on 2026-09-26: `npm run check:all` passed, including 20 configuration/CLI tests; `uv build` produced a source distribution and wheel; `uv run --locked urbanflow check-config --config configs/local.example.toml` validated the example profile. The run used macOS, Python 3.13.13, uv 0.11.8 and Node.js 26.7.0; the documented Node.js 24 baseline and Linux CI were not executed then. Later sections record observed engine and slice experiments. HTML edits received static checks only.

Preliminary source/spike evidence (2026-09-26): downloaded TLC January 2024 Yellow Taxi Parquet to ignored `.local/` storage; recorded its URL, retrieval date, SHA-256, full-file row count/schema/null counts and terms summary in the source contract. An initial PyIceberg + PyArrow run wrote and read back 100 rows in a local filesystem Iceberg table with a SQLite SQL catalog. The later shared-catalog spike below extends this evidence to PostgreSQL and Trino.

Shared-catalog spike (2026-09-26): PyIceberg 0.12.0 + PyArrow 25.0.1 wrote 2-row tables to both a file warehouse (`spike.pg_tiny` at `file:///…/.local/spike-iceberg/warehouse`) and an S3 warehouse (`spike_s3.tiny_s3` at `s3://warehouse`) via the same PostgreSQL SQL/JDBC shared catalog (`catalog_name=spike_pg` on the existing `urbanflow` Postgres). Trino 476 (connector `iceberg`, catalog type `jdbc`, `fs.native-local.enabled=true`, `fs.native-s3.enabled=true`, `s3.endpoint=http://s3mock:9090`) read both tables through `iceberg.spike.*` / `iceberg.spike_s3.*`, confirming `DESCRIBE` schema `(pickup_zone integer, fare_amount double)` and `count(*)=2` matching each writer. The executable spikes are `scripts/spike_iceberg_trino.py` (file) and `scripts/spike_iceberg_s3.py` (S3 via `adobe/s3mock:latest` at `localhost:9090`/`s3mock:9090`) using `.venv/bin/python`; configuration is `docker/trino/catalog/iceberg.properties` and `compose.yaml` (`postgres` + `s3mock` + `trino:476`; file warehouse needs dual mounts for Trino's `/tmp`-prefixed local filesystem, S3 does not). Details in `docs/spikes/2026-09-26-foundation-compatibility.md`.

Reproducible ingestion (2026-09-26): `src/urbanflow/ingestion/sources/nyc_taxi.py:download_yellow_taxi` enforces `working_data_peak_gb` via `_working_data_size_bytes` + `Content-Length`, writes checksum-addressed `bronze/raw/.../release=sha256-…/yellow_tripdata_YYYY-MM.parquet` with atomic `.incoming` + manifest `release_dir/manifest.json` (row_count/schema via `pyarrow.parquet`). Unit `tests/unit/test_ingestion.py` proves `unchanged` reuse, `refresh` correction as new SHA, transient retry, failed cleanup, and peak admission. CLI `urbanflow download-yellow-taxi` now passes `working_data_peak_gb` from `LocalSettings`.

First analytical slice (2026-09-26): `src/urbanflow/lakehouse/taxi.py:publish_yellow_slice` publishes `bronze.raw_yellow_trips`, `silver.clean_trips`, `silver.quarantine_yellow_trips` (reasons: missing timestamps, dropoff_before_pickup, invalid zone, negative fare/distance, passenger_count), and `gold.zone_hour_demand` `(city,zone,hour)` through `spike_pg` (file and S3). A deterministic 2,000-row January 2024 slice yields `input 2000 = accepted 1967 + quarantined 33`, `gold 79`; Trino table counts, Gold schema and a grouped query were verified. The manifest pins table snapshots. Details are in `docs/spikes/2026-09-26-ingestion-and-slice.md`.

Period-scoped publication (2026-09-27): publishing a new month appends its rows; republishing a month replaces rows for that period in Bronze, Silver, quarantine and Gold while retaining other months and previous snapshots. Legacy single-period quarantine and Gold schemas receive a period backfill before the first scoped write. `tests/unit/test_taxi_slice.py` seeds the legacy schema, publishes January and February, corrects January, repeats the correction, and confirms the other month and reconciled row counts remain. The test uses a disposable SQLite catalog; live table-query compatibility was verified in the earlier Trino slice. Separate Iceberg table commits are not atomic, and same-period concurrent writers are not coordinated.

Stage 1 completion (2026-09-28): added `download-yellow-taxi --latest`, which parses the official TLC monthly-link index and selects the newest valid Yellow Taxi Parquet period. The live index resolved to `2026-07` during verification; this records observed listing state, not a promise of future availability. Row-level deduplication is explicitly disabled because TLC supplies no stable trip-row ID; equal-valued rows are retained and every run reconciles `validated + rejected + duplicate_rows(0) = input`. An unchanged checksum is a download no-op, and period-scoped replacement prevents repeat publication from increasing row counts. Added `query-yellow-demand`, a read-only parameterized Trino query capped at 100 rows. It returned the local Gold demo row through the running Trino 476 service; the existing shared table predates `source_period`, so the live query was verified without a period filter. The source-time contract explicitly maps naive timestamps to `America/New_York`, adds UTC-normalized Silver fields, and quarantines DST-ambiguous/nonexistent times. Unit tests cover official-link parsing, missing links, duplicate preservation, DST boundaries, row reconciliation, CLI routing, bounded query parameters and result mapping. `npm run check:all` and `uv build` are the final gates for this milestone. Remaining lifecycle controls—scheduling, multi-table atomic release advancement and competing-writer coordination—are not Stage 1 deliverables.

The first stage should be independently demonstrable. It does not require NiFi, Kafka, Flink, Spark, Airflow, ML, and the agent all to be installed first. Choose the minimum viable table writer and shared catalog before building the foundation.

Correctness, authentication where exposed, secret handling, and basic instrumentation accompany each stage. Stage 7 consolidates and deepens those controls rather than introducing them for the first time.

Kubernetes, Terraform, Helm, automated lineage services, CDC, a feature store, enterprise integrations, a third city, and collision data remain extensions. Promote an extension only with a clear problem, a bounded experiment, and an explicit maintenance/cost trade-off.

## First implementation commits

These are commit-sized outcomes, not completed work or prescribed commit hashes. Each should carry its directly affected documentation and meaningful validation.

1. **Foundation compatibility and source contract:** choose exact catalog/writer/engine versions; write/read a tiny Iceberg fixture through the chosen writer and Trino; document DuckDB access mode. Specify identities, correction rules, timestamps and historical/latest release selection.
2. **Reproducible ingestion:** add source discovery, checksummed manifests, bounded download/retry and small fixtures. Demonstrate unchanged release, new period, corrected period and resource-admission behavior.
3. **First analytical slice:** Bronze/Silver/Gold, quarantine, one-trip trace, reconciled aggregate and frozen snapshot. Publish coverage/freshness; prove a refresh advances the current release without changing a pinned experiment.
4. **Modelling and scheduling:** validate dbt-trino, transfer Gold ownership, introduce parameterized Airflow refresh/backfill jobs and safe maintenance. Prove retry/overlap idempotency.
5. **First measured report and portal export:** run a bounded comparison under the benchmark protocol; validate a versioned export and create architecture/engineering/data portal pages.

Continue with streaming and the remaining stages once their dependencies are demonstrated. A small portal may ship before the final public-platform stage; Stage 8 integrates the completed capabilities. ML and agent work remain later scope. Local limits constrain execution plans, not the expandable architecture or support for both historical and latest published data.
