02 / What this system gives you

Intended outcomes · earned through working evidence
01 — UNDERSTAND

See mobility clearly.

Explore demand by city, zone and time. Compare historical patterns on a map and inspect weather or event context.

Proof to buildKnown aggregates reconcile to accepted, rejected and duplicate source counts.
02 — ANTICIPATE

Know what may come next.

Forecast demand at +15, +30 and +60 minutes. Surface unusual activity with supporting measurements.

Proof to buildOut-of-time MAE / RMSE versus seasonal baselines, with model and data versions.
03 — ASK

Get answers with evidence.

Ask “Which zones changed most?” Approved tools retrieve real results; the assistant explains the time range and freshness.

Proof to buildGrounding, SQL validity, permissions and injection evaluations. Context is not causation.
04 — PROVE

Understand the engineering.

Replay data, inject failures and study backpressure. Demonstrate how the system handles late events and duplicate records.

Proof to buildRepeatable benchmark and recovery reports, with hardware, configuration and limitations.

05 / Your technology field guide

The full learning universe, not a day-one install list

Before implementation: the decisions still open
  • Choose the Stage 1 table writer and a shared Iceberg catalog; validate engine and connector versions. Polaris / REST catalog is a candidate.
  • Choose Avro or Protobuf, a registry product, partitioning, retention, watermarks, late-data policy and deduplication identity.
  • Define ownership and reconciliation between batch, durable streaming tables and Redis. Checkpointing alone does not prove end-to-end exactly-once results.
  • Define finer-grained features for +15 / +30 / +60 minute forecasts; hourly Gold tables alone are insufficient.
  • Select authentication, an LLM provider, trace storage, model promotion gates and any production service targets.
