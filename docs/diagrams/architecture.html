What this platform is for

The project exists to answer one question end to end: what physically happens to a single taxi trip as it travels from a public dataset to a number on a dashboard. Every tool on the map earns its place by solving one problem that the tool before it cannot.

The claim it makes

  • Production-shaped lakehouse over real public mobility data
  • Batch and streaming over the same records
  • Measured engineering decisions, not installed tools
  • Reliability tested by breaking it on purpose

The claim it refuses to make

  • No petabyte or terabyte scale
  • No invented benchmark numbers — every figure comes from a run
  • No live NYC feed; the stream is a labelled replay
  • No always-on cloud cluster behind the demo

The design rule

For every component, in order: what production problem does it solve, what physically happens, how is it measured, how does it fail, how does it recover. A component that cannot answer all five is cut.

One trip, all the way through

The learning spine of the project. A hypothetical trip from zone 161 to zone 237, picked up at 18:31:42. Its project identity must follow the source contract; the example is not a real trace or a claim that TLC supplies a trip ID.

Batch path

  1. Published by NYC TLCmonthly parquet drop
  2. Downloaded by the ingestion jobpython adapter, checksum recorded
  3. Lands as an immutable objects3://urbanflow/raw/tlc/yellow/<period>/<release>/
  4. Becomes a row inside a row groupparquet, compressed, column-addressable
  5. Registered as a data file in a snapshoticeberg manifest entry
  6. Read, cleaned, enriched by Sparkbronze to silver, new parquet files
  7. Committed as a new snapshotolder snapshot queryable while retained and supported
  8. Queried interactively by Trinopartition pruning + predicate pushdown
  9. Aggregated away by dbtproposed Stage 2 dbt-trino; Stage 1 selected writer
  10. Served from a gold martgold.zone_hour_demand
  11. Rendered on the portalversioned exported json first

Streaming path, same record

  1. Read back from historical parquetreplay producer, rate-controlled
  2. Published with a partition keyproposed key = (city, pickup_zone), topic mobility.yellow
  3. Given a partition and an offsetillustrative partition/offset; configuration pending
  4. Consumed by Flink with event timewatermark derived from pickup_timestamp
  5. Placed in a five-minute windowstate keyed by city, zone and replay scope
  6. Deduplicated, late arrivals handledallowed-lateness and too-late routing policy
  7. Checkpointedrecovery point, not a result
  8. Emitted as a real-time aggregatetrips per zone per five minutes
  9. Written to an Iceberg sinkseparate table from the batch path

The data model

Proposed canonical tables match the data contracts. Bronze retains source fidelity, Silver validates and normalizes, Gold defines business grains. Census and additional marts remain optional.

Bronze — source shape

  • raw_yellow_trips — source shape and release provenance
  • raw_weather
  • raw_events, raw_traffic — later sources

Preserve source-release bytes and provenance. Corrections create a new release; validation and normalization occur downstream. Retention remains explicit.

Silver — cleaned and joined

  • clean_trips — validated rows; rejected rows retain quarantine evidence
  • normalized_events, normalized_traffic
  • normalized_weather
  • geographic_reference

Derived here: trip_duration_seconds, average_speed, valid-zone flag.

Gold — business answers

  • zone_hour_demand
  • zone_hour_features
  • forecasting_features
  • mobility_anomalies
  • model_predictions

The initial portal reads validated Gold exports with version and freshness metadata. Later APIs can expose current state and model outputs.

Failures worth engineering on purpose

Bad data

  • negative fare, negative distance
  • dropoff before pickup
  • zone_id that does not exist
  • duplicate trip_id
  • null timestamp

Bad files

  • bounded small-file fixture versus compacted files
  • then compact and re-measure

Bad distribution

  • synthetic hot-zone skew fixture
  • one Spark worker becomes a straggler
  • fix with salting or repartition

Bad luck

  • kill Kafka mid-stream
  • kill a Flink task manager
  • fail a Spark task
  • roll back a bad Iceberg snapshot

Local profile, expandable system

The local host has 16 GB RAM and a 512 GB SSD. Resource policies belong in deployment configuration, not business logic. Services run selectively; larger deployments can retain more history and scale workers through the same contracts.

Local admission budget

  • About 10 GB routine working data; 20 GB peak maximum
  • Count raw and curated copies, snapshots, Kafka logs, checkpoints, exports, telemetry and rewrite scratch
  • Track container images separately; aim for 100+ GB free SSD
  • Provisional 8–10 GB stack RAM; measure actual service use
  • Keep selected historical periods plus a recent window; pause new work if protected history and a refresh cannot fit

Configurable modules

  • Source discovery and adapters independent of transforms
  • Shared object storage and compatible Iceberg catalog
  • Finite batch/modelling jobs; separate Kafka/Flink runtime
  • Optional product, ML and observability profiles
  • Versioned API/export contracts; configurable endpoints, retention, concurrency and partitions

Start with 100–500 MB inputs; expand only after measuring storage amplification and peak scratch. Input size is not total working-set size. Local design · Expansion boundaries

Historical and latest, together

Frozen historical runs and ongoing latest-source refresh share adapters, manifests, validation and publication rules. Latest means the newest validated published release, not a live NYC feed.

  1. Discover and identify source releasesperiod, version/checksum, publication time if known, observed time
  2. Admit a bounded runseparate refresh/backfill queues, peak disk and memory checks
  3. Validate and reconcileunchanged release is a no-op; corrected periods replace or merge under explicit rules
  4. Publish a consistent releasemanifest pins table snapshots; conditional publication prevents stale jobs replacing newer releases
  5. Retain history deliberatelyprotect experiment snapshots; scale storage/retention beyond local profile when needed

Delivery sequence

The original eight stages remain the canonical roadmap. The near-term engineering slice adds modelling, maintenance and a small export-backed portal. Every stage remains planned.

Stage 1

Data foundation

Catalog/writer compatibility, historical slice, latest-release contract, Bronze/Silver/Gold and one reconciled query.

Stage 2

Distributed processing

Spark transforms, proposed dbt-trino Gold models, DuckDB comparisons, Airflow refresh/backfill and maintenance.

Stage 3

Streaming

Versioned contracts and registry, Kafka replay, Flink windows, separate rt tables, recovery reconciliation; Redis with live serving.

Stage 4

Multi-source / multi-city

Weather, events, traffic and later Chicago. Census remains optional; geography and availability are explicit.

Stage 5

ML

Temporal baselines, forecasts and anomaly evaluation, MLflow, versioned inference and rollback.

Stage 6

Agent

Authorized tools, bounded read-only SQL and evidence-grounded responses, with security evaluations.

Stage 7

Production hardening

Broader operational, security, load and failure evidence. Basic correctness and telemetry start in Stage 1.

Stage 8

Public platform

Integrate completed capabilities and measured reports. Architecture/engineering/data pages may ship earlier.

Exit evidence and first implementation commits. Optional cloud validation tests portability; it does not prove production capacity.

Tier 1 — engineering environment

Your Mac. 10–20 GB of real data, the full lakehouse and streaming stack under Docker profiles. This is where the engineering happens and where every benchmark is produced.

Tier 2 — public serving

Bounded validated Gold exports, with payload size measured per page. Start with generated JSON read by a static Next.js build; add a small database only when a page genuinely needs to query rather than read.

Expanded deployment reference

Storage, catalog, Kafka, Flink, Spark and Airflow can be deployed remotely when needed. Keep data/control services private, configure retention and capacity independently, and test migration and recovery.

Architecture decision gates

Findings from the supplied review are reconciled with the earlier design. These are requirements and proposed directions; implementation evidence is still pending.

Planned

Catalog compatibility

Required before foundation implementation: choose a catalog product and writer using pinned Spark/Trino/Flink compatibility tests. REST is a candidate interface, not proof of universal support. Optional discovery/lineage tools do not replace this catalog.

Planned

Table ownership

Spark owns Bronze-to-Silver; proposed dbt-trino owns Silver-to-Gold from Stage 2 after adapter/materialization tests. Flink owns separate rt tables. Stage 1 uses one temporary Gold writer and transfers ownership explicitly.

Planned

Latest releases and corrections

Coordinate overlapping refresh/backfill runs. Record source revisions, replace or merge corrected periods safely, publish snapshot manifests and keep frozen experiments reproducible.

Planned

Maintenance and retention

Define retention and pins with the first write. Budget rewrite headroom and test compaction before sustained streaming. Expiry/orphan cleanup must protect active writers, recovery and pinned experiments.

Planned

Benchmark fairness

One engine at a time, comparable total resources, identical semantics and checked results. Separate startup and cache conditions. Warm series: one discarded warm-up, median/range of at least five runs. Report raw results and limitations.

Planned

Geography and deferred tools

Keep weather observation geography explicit. Census needs a versioned crosswalk and measure-specific aggregation. Defer ClickHouse, OpenMetadata and additional ingestion frameworks until their workload justifies them.

Planned

Tests and evidence

Code, contract and recovery tests accompany data checks. No benchmark, capacity, monthly cost or provider compatibility claim is established by these diagrams.
